# AI 设计、代码导出、备份与 Agent 集成：评估

> 评估日期：2026-09-27。当前状态：**只有评估，一行代码都没写**。
> 结论都限定在「当前版本」（v0.4.0，14 种数据库，无任何 AI 能力、无任何网络服务依赖）。
> 每条「不做 / 后做」都带重估条件。

用户提了四件事：

1. 用 AI 把开发者的想法变成数据库设计：关系库出表与 ER 图，Neo4j 出图模型，MongoDB 出 JSON，
   可视化、确认后再创建。
2. 导出：用 AI 生成特定框架（NestJS、Next.js、Spring Boot…）的数据库相关代码；SQL 导出；
   常见数据库的备份。
3. 生成 Agent Skill 与 MCP。

## 0. 结论（按建议的先后）

| # | 功能 | 结论 | 规模 | 为什么 |
| --- | --- | --- | --- | --- |
| A | **AI 设计新库 → ER 图 → 确认后建** | **做，第一个**；先只做关系库 | 大（新领域） | 现成的零件最多：ER 渲染、各方言 DDL、预览、风险确认都在；缺的是一个多表模型与 AI 调用本身 |
| B | 导出为 `INSERT` 语句 | **做**，小 | 小 | 导出管线与双实现语料都在，加一种格式 |
| C | 整库结构导出（DDL 脚本） | **做**，中 | 中 | A 要用同一个「多表模型 → DDL」，顺手得到 |
| D | 备份 | **只包装官方工具**，不自己实现 dump；SQLite / DuckDB 用自带能力 | 中 | 自己写的 dump 恢复不回去比没有更糟 |
| E | 数据字典 / Agent Skill 导出 | **做**，小；排在 C 之后 | 小 | 就是 C 的另一种输出格式（Markdown + frontmatter） |
| F | 框架代码（Prisma / TypeORM / JPA …） | **后做**，且**不用 AI**，用确定性模板 | 中 | 从目录到实体是纯映射，AI 只会引入不稳定；生态里已有 `prisma db pull` 等工具 |
| G | DataOmni 作为 MCP 服务 | **单独立项评估，当前不做** | 大 | 价值真实，但等于把用户的生产库交给 Agent；安全面比 A 大一个量级 |
| H | Neo4j / MongoDB 的 AI 设计 | **A 落地后再做** | 中 | 这两家「创建」这一步很薄（约束、索引、校验规则），价值主要在可视化 |

**一条贯穿所有 AI 功能的原则：AI 只产出结构化的模型（JSON），不产出要执行的语句。**
DDL、Cypher、`createCollection` 一律由现有的确定性代码生成，走现有的预览与风险确认。
理由是这个仓库最值钱的东西就是「每条发出去的语句都有门守着」：
方言引号、`fixtures/*conformance*` 语料、`statementRisk`、生产环境确认。
让 AI 直接写 SQL 等于在这些门旁边开一扇侧门——而且它写出来的 SQL 我们没法验证，
我们自己生成的 SQL 可以。

## 1. 现状：哪些零件已经在

逐项核过代码，不是凭印象：

- **ER 图**（`utils/erLayout.ts` + `ErDiagramView`）：输入是 `ErTable[]` + `ErLink[]`，
  布局是纯函数，与数据来源无关。**一份 AI 给的模型换成这两个数组就能画**，不用改布局。
  已有搜索、缩放、SVG / PNG 导出。
- **建表 DDL**（`utils/tableDdl.ts` 的 `buildCreateTable`）：按方言拼 `CREATE TABLE`，有语料测试
  （`tableDdl.conformance.test.ts`）。**只管一张表，没有外键**；索引在 `objectDdl.createIndexSql`。
- **预览与确认**：`DdlPreviewDialog`、`DestructiveStatementPrompt`、`statementRisk`、
  连接上的 `environment`（生产环境门槛更高）。
- **Neo4j**：`CypherGraphView` 已经会画节点与关系（手写 SVG）。
- **MongoDB**：`MongoCreateCollectionDialog` **不支持 validator**（`$jsonSchema`）。
- **导出**：CSV / JSON，流式写文件、可取消、`.part` 改名、任务中心；格式化两份实现由
  `fixtures/export-conformance.json` 钉住。**没有 SQL 格式，没有整库结构导出，没有备份。**
- **网络与凭据**：后端有 reqwest（Elasticsearch、ClickHouse 在用）、钥匙串存密钥
  （`connection_service` 的 keyring）。API Key 放钥匙串是现成的路。
- **AI**：**完全没有**。`TODOs.md`「暂不优先」里有一条「AI 自动执行写操作」——下面的设计
  始终要人确认，不和它冲突。

## 2. A：AI 设计新库（关系库）

### 2.1 流程

```
一句话需求 ──► AI（结构化输出）──► SchemaDraft（JSON）──► 校验 ──► ER 图 + 表格编辑
                     ▲                                                     │
                     └──────────── 追加要求 / 手工改 ◄─────────────────────┘
                                                                           │ 确认
                                             按外键依赖排序 ◄──────────────┘
                                                   │
                                   buildCreateTable ×N + 外键 + 索引（确定性）
                                                   │
                                        DdlPreviewDialog ──► 执行（逐条，报告停在哪）
```

### 2.2 缺的零件（这就是工作量）

1. **`SchemaDraft` 多表模型**：表、列（复用 `ColumnDraft`）、主键、外键、索引、注释。
   它是 AI 输出、ER 图输入、DDL 输入三者之间唯一的中间形态。
2. **外键进 DDL**：`buildCreateTable` 现在没有外键。建表要按依赖拓扑排序；有环时先建表，
   外键之后用 `ALTER TABLE … ADD CONSTRAINT` 补。SQLite 不支持事后加外键，有环就只能拒绝。
3. **校验**（纯函数，AI 输出进来第一道）：列类型是否属于该方言、外键两端的类型是否一致、
   引用的表和列是否存在、名字是否撞了保留字或已有的表。**校验失败不静默修**，列出来，
   可以把错误回给 AI 让它改。
4. **AI 调用**：见 §6。
5. **界面**：一个新的标签页类型（像 ER 标签那样），左侧是对话与表格编辑，右侧是 ER 图。

### 2.3 必须写明的边界

- **只建新表，不改已有的表。** 「按需求改现有结构」要生成 ALTER、要考虑数据迁移，
  `buildTableDdl` 连改主键都明确不做。重估条件：有人拿着一个「给现有库加功能」的具体需求来。
- **MySQL 的 DDL 不在事务里**（隐式提交），建到第五张失败时前四张已经在了。预览里照实说，
  和 TiDB 改表名拆句那条同一个处理办法；PostgreSQL / SQL Server 可以整批放进事务。
- AI 只看**结构**（已有表名、列名，用来避开重名），**不看数据行**；每次发出去的内容要能在界面上看到。

### 2.4 先做的实验（动手前，半天）

判断「值不值得做」的是一个数：**AI 给出的模型有多少能一次通过校验**。
拿 10 条典型需求（博客、电商订单、多租户 SaaS、预约系统…），各跑 3 次，统计：
JSON 合法率、通过 §2.2 第 3 条校验的比例、人工看「设计合不合理」的比例。
- 一次通过率很低 → 重心要放在「校验 + 回给 AI 修」的循环上，界面设计也要跟着变；
- 高 → 按上面的流程直接做。

这个实验不需要写应用代码：一段脚本 + 校验函数就够，而校验函数本来就要写。

## 3. B / C / E：确定性的导出

- **B：导出为 `INSERT`**。加在现有导出对话框的格式里，前后端两份格式化照旧由语料钉住。
  要处理的是各方言的字面量（二进制、日期、布尔、`NULL`），`sqlLiterals.ts` 已有一部分。
  选项：每行一条 / 多行合一条、要不要带列名。
- **C：整库结构导出**。复用 A 的 `SchemaDraft → DDL`：先把目录读成 `SchemaDraft`，
  再生成脚本。MySQL 可以直接用 `SHOW CREATE TABLE`（原样最准），PostgreSQL 没有等价物，
  只能自己拼——视图、触发器、序列、函数的覆盖面要写明，**覆盖不到的列出来，不悄悄略过**。
- **E：数据字典 / Skill**。同一份模型输出成 Markdown：每张表的列、类型、主外键、注释。
  加一段 frontmatter 就是一个 Agent Skill（`SKILL.md`），Agent 读了就知道这个库长什么样。
  **表和列的说明文字**才是 AI 能帮上的地方（按名字猜用途），而且要标注「推测」。

## 4. D：备份

**不自己实现 dump。** 一个能导出但恢复不回去的备份比没有备份更危险——用户以为有备份。
各家官方工具覆盖了序列、触发器、权限、编码、大对象这些我们一时覆盖不全的东西。

| 数据库 | 做法 |
| --- | --- |
| SQLite | `VACUUM INTO '文件'`，自带、一致、一条语句 |
| DuckDB | `EXPORT DATABASE '目录'`，自带 |
| MySQL / MariaDB | 调 `mysqldump`（找得到才给这个按钮） |
| PostgreSQL | 调 `pg_dump`（同上；要注意客户端版本不能低于服务端） |
| MongoDB | 调 `mongodump` |
| 其余 | 不做 |

经 SSH 隧道时要把外部工具指到本地转发端口；密码经环境变量（`MYSQL_PWD`、`PGPASSWORD`）传，
不写进命令行（`ps` 看得见）。进度和取消复用任务中心。

## 5. F：框架代码生成

**当前版本不做，做的时候也不用 AI。**

- 从表结构到 Prisma schema、TypeORM 实体（NestJS）、Drizzle（Next.js 常用）、
  JPA 实体（Spring Boot）是**确定性映射**：类型对照表 + 模板。确定性的东西用 AI 做，
  只会把「每次一样」变成「每次不一样」，还没法测。
- 生态里已经有维护得很好的工具：`prisma db pull`、`drizzle-kit pull`、
  IntelliJ / JPA Buddy 的逆向工程。DataOmni 在这里的增量有限。
- AI 真正能帮上的是「按这张表生成一套 CRUD 接口」这种有发挥空间的代码，但那是代码助手
  （Claude Code、Cursor）的主场，它们看得到整个项目，我们看不到。

**重估条件**：A 落地、有了 `SchemaDraft` 之后，「设计完直接拿到 Prisma schema」是顺手的一步
（同一个模型多一种输出）；先只做 Prisma 一种，有人要第二种再加。

## 6. AI 调用本身（A、E、H 共用）

- **在后端调**（Rust + reqwest），不在前端：API Key 不进 WebView。Key 存钥匙串，和数据库
  密码同一套。
- **结构化输出**：用工具调用 / JSON Schema 约束输出成 `SchemaDraft`，不解析自由文本。
- **供应商**：先接一家（Anthropic Messages API，默认 `claude-sonnet-5`），留一个
  「OpenAI 兼容地址」让本地模型（Ollama 等）可用——**有第二家的真实需求再抽象**，
  不先搭多供应商框架。
- **发出去什么要看得见**：设置里有开关，默认关；每次请求前能展开看到完整的提示词与附带的结构信息。
  连接标为生产环境时，默认不附带它的结构。
- 超时、取消、错误原文照其它网络请求的规矩。

## 7. G：DataOmni 作为 MCP 服务

价值是真的：让 Claude Code 之类的 Agent 用上用户在 DataOmni 里配好的连接（含 SSH 隧道、
钥匙串密码），查结构、跑只读查询。但它等于**把用户所有的库交给一个会自己决定发什么语句的程序**。
至少要先回答：

- **怎么跑**：stdio 要一个独立进程，读得到钥匙串（每次重新签名都会弹授权框，见 GUI 测试的教训）；
  或者应用内开一个只监听本机、带令牌的 HTTP 端点——应用不开着就用不了。
- **权限**：按连接逐个开放、默认只读（复用 `statementRisk` 拒绝写语句）、生产环境不开放、
  结果行数上限、每条语句留审计记录。
- **和现成工具比**：各家数据库都已有 MCP 服务；我们的增量是「一处配置管 14 种库 + 现有的风险门」。

**当前不做。重估条件**：用户确认「让 Agent 直接查自己配好的库」是日常要用的工作流；
那时单独写设计说明（像 `rfcs/ssh-tunnel.md` 那样），验收门里必须有「写语句被拒」「生产连接不可见」
两条该红的用例。在那之前，E 导出的 Skill（静态的库结构说明）已经能覆盖「让 Agent 了解这个库」的大半需求。

## 8. H：Neo4j / MongoDB 的 AI 设计

- **Neo4j**：模型是节点标签、关系类型、属性、唯一约束与索引。可视化复用 `CypherGraphView`，
  「创建」这一步只是几条 `CREATE CONSTRAINT` / `CREATE INDEX`（Neo4j 本身不需要建表）。
  价值主要在「把想法画出来」，可以再附一小份示例数据的 Cypher。
- **MongoDB**：模型是集合、示例文档、`$jsonSchema` 校验规则、索引。先要给
  `MongoCreateCollectionDialog` 补上 validator。
- 两者都等 A 把「AI → 模型 → 校验 → 可视化 → 确认」这条路走通再做，复用它的界面与 AI 调用。

## 9. 建议的顺序

1. **§2.4 的实验**（半天）——决定 A 怎么做，甚至做不做。
2. **B：`INSERT` 导出**（小、独立，可以和 1 并行）。
3. **A 的非 AI 部分**：`SchemaDraft`、外键与依赖排序、校验、从目录读成 `SchemaDraft`。
   这一步本身就产出 **C：整库结构导出**，不依赖 AI 也有用。
4. **A 的 AI 部分**：§6 的调用 + 设计标签页。
5. **E：数据字典 / Skill 导出**。
6. **D：备份**（SQLite / DuckDB 先，外部工具后）。
7. H、F、G 按各自的重估条件。
