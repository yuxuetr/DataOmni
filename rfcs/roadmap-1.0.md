# 1.0 规划与之后的路线

> 2026-10-06 定稿时的状态：v0.5.1 已发布。本文跟代码走；任务的勾选状态在 `TODOs.md`「v1.0」里维护，
> 这里只写为什么、做到什么程度算完、哪些不做。

## 一、现状

功能面已经铺开：TODOs 里 P0–P4、P6 都已勾上，P7 做完了能做的部分（KingbaseES 卡在拿不到安装包）。
兼容性矩阵 17 行，每一行都有真库用例。前端约 7.3 万行，Rust 约 3.1 万行，前端测试 1910 条。

缺的不是功能，是这三样（2026-10-06 查的数）：

| 事实 | 数据 | 意味着什么 |
| --- | --- | --- |
| 用户 | GitHub 星标 0、issue 0；v0.5.1 五个安装包下载数都是 0 | TODOs 里几十条「重估条件：有人提 / 有人报」**一条也不会触发**；照现在的规矩，项目会停在原地 |
| 打包版里出了错能不能说清 | 后端只有 14 处 `println!`，打包版没有控制台，这些输出谁也看不到；没有日志文件 | 第一份缺陷报告只会有一句「连不上」 |
| 升级会不会丢东西 | `connections.json` 是不带版本号的数组，`db_type` 是没有兜底分支的枚举；查询历史与工作区快照在版本号对不上时**整份丢弃**（`queryHistoryStorage.ts`、`workspacePersistence.ts`） | 以后加一种连接类型，用户退回旧版时所有连接都读不出来（**这条是从类型推出来的，没实测**，R1 第一步就是用一条测试确认）；以后改快照格式，升级时历史和打开着的标签会悄悄清空 |

所以 1.0 的重点不放在新功能上，而是把**已有的东西做成能长期托付的样子**，让第一批用户进得来，
出了问题也能报得回来。

## 二、1.0 承诺什么

1.0 之后要守语义化版本。下面四条是对用户的承诺，每条都配一个能执行的验收：

1. **三个平台都能安装、升级、卸载干净。** 验收：在 CI 产出的包上（不是本机构建）走完 `docs/release-regression.md`，
   Windows 再走 `docs/windows-checklist.md`。
2. **升级不丢东西，降级不毁东西。** 从 0.5.1 起的任何版本升到 1.x，连接、钥匙串里的口令、标签与草稿、查询历史、设置都还在；
   退回较旧的 1.x，读不懂的那一条只是跳过，**不能连累别的条目**，也**不会在保存时被删掉**。
   验收：把 0.5.1 写出的每一种落盘文件存成固定样本，永久保留一条「这些样本必须读得出来」的测试。
3. **出了问题能说清楚。** 有日志文件，口令不进日志；「关于」里可以复制诊断信息（版本、系统、架构、WebView 版本）。
   验收：用一条门扫描日志调用点，带口令的字段写进去就变红。
4. **有新版本时用户会知道。** 验收：把 latest 指到一个更高版本号的测试 Release，旧版能看到提示。

**1.0 不承诺**：兼容性矩阵里标 ⚠️ 的各项缺口原样保留（它们已经写在 README 里）；不新增数据库，也不新增功能。
1.0 前只修回归中发现的缺陷。

## 三、1.0 前的任务（按顺序）

### v0.6.0：稳定化

- **R0 TODOs.md 再归档一次。** 现在 250 KB，规矩是到 100 KB 左右就归档。先做这一步，后面每次读它都更省。
- **R1 落盘格式盘点与兼容门。**
  - 盘点：`connections.json`、约十个 localStorage 键、钥匙串条目的命名（`CREDENTIAL_SERVICE` 加连接 id）、
    导出连接文件（已带 `format` 与 `version`）。
  - 先写一条该红的测试：`connections.json` 里有一条未知的 `db_type`，其余连接仍应读得出来。
  - 改法：
    - 逐条解析。读不懂的那一条把原文留在内存里，保存时原样写回。
    - 历史与快照遇到更新的版本号时，不再整份丢弃，改为不覆盖：这一轮只读，不回写。
  - 固定样本放在 `fixtures/on-disk-0.5/`。
  - 不做：通用的迁移框架。格式第一次真要升版本时再写那一步迁移，到时样本测试会先变红。
- **R2 日志与诊断信息。**
  - 写进应用的日志目录，按大小轮转，设置里有「打开日志目录」。
  - 把现有的 `println!` 换掉，不新增埋点。
  - 「关于」里加「复制诊断信息」。
  - 门：日志调用点不许出现 password / secret / credential 字段。
- **R3 新版本提示。**
  - 启动时最多每天查一次 GitHub Releases 的 latest，有新版本就显示一条横幅，链接到 Release 页面。
  - 设置里可以关掉（这是联网，要让用户能关）。
  - **为什么必须在 1.0 做**：提示只能装在用户**先装上**的那个版本里。1.0 不带它，装了 1.0 的人以后就永远不会知道 1.0.1 出了。
  - 不做：应用内下载并替换。这需要长期保管一把更新签名私钥，还要在 Release 工作流里生成 `latest.json`。
    重估条件：第一次出现必须让用户尽快升级的缺陷（比如安全问题），或者有人提出这个需求。
- **R4 反馈入口。**
  - GitHub issue 模板两种：缺陷（让人贴上诊断信息）、想连的数据库或部署形态。
  - 只是两个 YAML 文件，但它让「有人提」那些条件第一次有机会触发。

### v1.0.0-rc.1：三平台验收

- **R5 Windows 安装验证。** 分两半：
  - **CI 能做的放进 CI**：在 `windows-latest` 上静默安装 MSI 与 NSIS（`msiexec /qn`、`/S`），确认主程序起得来、
    活过 N 秒，查注册表与开始菜单项；再升级一次、卸载、确认没有残留。每次发版都跑，不靠人记得。
  - **必须人看的**：首次运行的 SmartScreen 提示、界面走一遍、带 Instant Client 连 Oracle。
    这需要一台没在跑别的东西的 Windows 机器。本机 Parallels 的虚拟机是 ARM 的，里面开着交易软件，**不在上面自动化**。
- **R6 兼容库与 SSH 隧道的打包版回归。**
  - 范围：OceanBase、openGauss、MariaDB、TiDB、CockroachDB、SSH 隧道。
  - 这些后端用例都过了，但还没在打包版的界面里走过。
- **R7 完整回归后发 1.0。**
  - 在 CI 产出的三个平台的包上走完回归清单，回归中修的每一处都在新包上复验。
  - 然后勾上「P0–P3 无阻塞级缺陷」和「完成 P5」，打 `v1.0.0`。

## 四、1.0 之后的路线

原则不变：**先有证据再做**。不同的是，1.0 之后证据可以来自用户了。下面按「哪一步能解锁后面的」排序。
除第 1 条外都是候选，不是承诺。

1. **让人用上（1.0 后首先做）**
   - 渠道：英文 README 与截图（界面早就有英文，README 只有中文）；上架 Homebrew Cask、winget；在中文与英文社区各发一次。
   - 能执行的度量：`gh api repos/yuxuetr/DataOmni/releases --jq '[.[].assets[].download_count]|add'` 和 issue 数。
     两个数都一直是 0，说明问题出在渠道，不在功能。
2. **日常工作的深度**。按能复用多少现有代码排序：
   - **已有库的 ER 图**：读外键元数据，转成 `SchemaDraft`，交给 A4 现成的 ER 图组件。新写的代码主要是元数据转换。
   - **两个库的结构比对与同步脚本**：两份 `SchemaDraft` 做差异，再用 A2 现成的 DDL 生成与依赖排序。
     这是 Navicat / DBeaver 的常用功能。
   - **`execute_query` 支持绑定参数**：带参数的查询与查询模板（4.4 的重估条件）随之解锁，
     表结构查询也能离开 `tauri-plugin-sql`，统一成一条解码路径（2.4 剩下的那项）。
   - 证据现在只有「同类产品都有」，还不是「用户要」。等第 1 条有了用户，按反馈排先后。
3. **AI 与 Agent**
   - **A8：DataOmni 作为 MCP 服务**。让 Agent 用已经配好的连接查库，并沿用应用自己的安全门：只读，生产连接不可见。
   - **A7：只生成 Prisma 一种**。
   - 两条的重估条件都已写在 TODOs 里。
4. **更多部署形态**
   - Redis 集群与 Sentinel、Neo4j 集群路由、Elasticsearch API Key。
   - 都等有人拿着这种部署来（R4 的模板里专门有这一类）。
5. **更多平台与库**
   - KingbaseES、达梦（顺带做 B4），Windows ARM64、macOS Intel。
6. **签名与信任**
   - 拿到 Developer ID 后：公证，加上完整的应用内更新。

**1.x 的版本号规矩**：

- 升主版本号：落盘格式、导出文件格式、钥匙串条目命名的不兼容改动。
- 升次版本号：新功能。
- 升修订号：缺陷修复。

R1 的样本测试就是主版本号的守门。
