# 更多数据库、国内版与 AI：版本与分支怎么管

> 评估日期：2026-09-27。当前状态：**只有评估**。结论限定在当前版本（v0.4.0）。

## 0. 结论

**不按版本开长期分支。** 一条 `main`，不同「版本」（国际版 / 国内版 / 不带 AI 的内网版）是
**同一份代码的不同构建组合**，靠三样东西区分：

1. **Cargo feature 决定编进哪些驱动**（和要不要 AI）；
2. **Tauri 配置覆盖文件决定带哪些资源、叫什么名字**（现成的做法：`tauri.oracle.conf.json`）；
3. **运行时由后端报告「这个构建有哪些驱动」**，前端照着显示，前端没有构建开关。

**驱动还不用引入 feature**：所有驱动都在一个包里、没有一家需要按版本区分，
第一个触发条件出现时（§4）再做。**AI 从第一行代码起就放在 `ai` feature 后面**（2026-09-27 定，§6）——
它是整块新增的附加功能，一开始就隔开比事后从各处摘出来便宜得多。

分支只用在两处：短命的功能分支；需要给旧版本打补丁时从 tag 切出的 `release/x.y` 维护分支。

## 1. 为什么不开长期分支

- 每个修复要合进 N 条分支。这个仓库一个功能平均动 20–30 个文件（ClickHouse 一次就是这个量），
  而 `models/mod.rs`、`databaseSupport.ts`、`i18n/zh.ts` 这几个**登记表**几乎每个功能都要改——
  长期分支在这几个文件上会一直冲突。
- 这个仓库吃过的亏里，最常见的一类是「**两份实现各自为政、谁也没比过谁**」：导出格式化的两份实现
  （所以有了 `export-conformance.json`）、连接串的两份实现（`c37aa96`）。长期分支就是整个仓库规模的
  两份实现，而且没有语料能钉住它们。
- 仓库里的门（「每种库都有驱动」「目录查询覆盖所有类型」等）在分支上会各自漂移，门就不再是门。

## 2. 版本差异到底在哪

把「国内版要什么」拆开看，绝大多数不是代码分叉，而是**构建组合和默认值**：

| 差异 | 放在哪 |
| --- | --- |
| 多几个国产库驱动（达梦等要原生客户端库的） | Cargo feature + 配置覆盖文件带客户端库 |
| 协议兼容的国产库 / 云库（大多数） | **不需要区分**，所有版本都有（见 §3） |
| AI 供应商默认值（国内模型） | 运行时设置里的预设列表，按版本给不同默认值 |
| 完全不能出网的内网 / 信创环境 | Cargo feature `ai` 关掉：代码不在二进制里，可以被验证 |
| 自动更新地址、应用名 | 配置覆盖文件 |
| 界面语言 | 已经有中英文，不是版本差异 |
| 信创平台（麒麟、统信；arm64、LoongArch） | 构建目标，不是代码分支（风险见 §6） |

**版本号所有版本共用一套**（都是 0.5.0），版本名写在安装包文件名和「关于」里
（`DataOmni-CN_0.5.0_aarch64.dmg`）。各自编号会让人说不清「这个修复在哪个版本里」。

## 3. 要接的库，按「要不要新驱动」分

大多数「新库」其实是**协议兼容库**，走现有驱动，做法和 MariaDB / TiDB / CockroachDB 一样
（TODOs 4.2「协议兼容库」：连真库跑现有用例、归因、修应用缺陷、写明缺口）。它们不需要任何版本区分。

| 类别 | 例子 | 驱动 | 主要风险 |
| --- | --- | --- | --- |
| MySQL 协议 | OceanBase（MySQL 模式）、PolarDB-X、TDSQL、GoldenDB、Doris、StarRocks、云上 RDS / Aurora | 现有 sqlx | 目录表的差异（TiDB 那种）；分析库没有事务 |
| PostgreSQL 协议 | 人大金仓 KingbaseES、openGauss、GaussDB、PolarDB-PG、瀚高、云上 RDS / Aurora / Neon / Supabase | 现有 sqlx | **openGauss / GaussDB 默认用 sha256 认证，标准 PostgreSQL 驱动不认**，要先做实验；连接池（PgBouncer 事务模式）不支持预处理语句，而 sqlx 用的是预处理 |
| SQL Server 协议 | Azure SQL | 现有 tiberius | Entra ID 认证 |
| 要新驱动 | 达梦 DM、OceanBase（Oracle 模式）、GBase 8s | 原生客户端库（C / ODBC） | 客户端库**能不能随包分发**要看许可；不能就只能让用户指定本机已装的客户端路径 |
| 云上的新协议 | Snowflake、BigQuery、Redshift Serverless Data API、DynamoDB | HTTP（复用 `http_endpoint.rs`） | 各自的认证（OAuth、IAM）；DynamoDB 是新的数据模型 |

**云数据库的差异主要在认证和网络，不在方言**：AWS RDS IAM 令牌、Azure Entra、GCP Cloud SQL
Auth Proxy、各家的 CA 证书包。这些是连接层的增量（像 SSH 隧道那样），对所有版本都有用。

## 4. 什么时候引入 feature（重估条件）

出现以下任一条时引入，在那之前照现在的做法直接在 `main` 上加：

1. 第一个**客户端库不许随包分发**、或只在部分平台有的驱动（达梦最可能是第一个）；
2. ~~有人要一个不含 AI 的构建~~ 已定：AI 一开始就是 feature，不再是触发条件；
3. 包的大小成为问题（现在 171 MB，其中 Oracle Instant Client 83 MB）——比如国内版不想带 Oracle 客户端。

## 5. 引入时怎么做（设计要点）

- **`DatabaseType` 枚举不加 `cfg`**，所有版本都认得所有类型。否则国内版导出的连接配置在国际版上
  整份读不出来。只把**驱动模块和它的分支**放进 feature；没编进来的类型，连接时报
  「这个版本没有带这个驱动」，界面上照样列出连接，只是连不了。
- 后端加一个命令报告编进了哪些驱动，前端的 `databaseSupport` 据此过滤新建连接的类型——
  前端不需要自己的构建开关，也就不会和后端对不上。
- 现有的门改成**按 feature 成立**：「每种库都有驱动」变成「每个开了 feature 的库都有驱动」。
- **CI 至少构建两套组合**（默认全开、国内版组合），否则没人用的那一套会悄悄编不过。
  现在 CI 只跑一套。
- 如果以后有收费的专业版功能：放在**单独的私有 crate / 仓库**，作为 feature 依赖接进来，
  而不是一条分支。

## 6. AI 功能在版本上怎么放

- **2026-09-27 定**：一条 `main`，AI 整块放在 Cargo feature `ai` 后面。正式安装包打开，内网 / 信创构建不开
  （代码不在二进制里，可以证明不出网）。编进来之后仍是设置里的开关，默认关。
- 接口只做两种模式：**Anthropic** 与 **OpenAI 兼容**。国内常用的模型服务（DeepSeek、通义千问、智谱、Kimi 等）
  与本地的 Ollama 都提供 OpenAI 兼容接口，所以「国内版」只是预设列表的默认值不同，**不需要第二套调用代码**。
- 前端不设构建开关：后端报告这个构建有没有 AI，没有就不显示入口。CI 构建开与不开两种组合。
- 设计细节见 `rfcs/ai-design-and-export.md` §6。

## 7. 信创平台（单独的风险）

麒麟、统信常见的是 Linux arm64，部分是 LoongArch64。arm64 的 Linux 包和现在的 x86_64 deb / rpm
是同一套做法，风险小；**LoongArch 上的 WebKitGTK 和 Tauri 很少有人走过**，在承诺之前要先在真机或
镜像里试一次能不能编、能不能跑。重估条件：有人明确要 LoongArch。

## 8. 建议的顺序

1. 先接**协议兼容**的国产库和云库，一次一个，走 4.2 的兼容性验证流程，不动版本结构。
   第一个建议 KingbaseES 或 OceanBase（MySQL 模式）：用户多、有社区版镜像。
   openGauss 先做 sha256 认证的实验。
2. 云库的认证（RDS IAM 等）按有人要的顺序加，所有版本都有。
3. 达梦这类要原生客户端的库到来时，按 §5 引入 feature 和第二套 CI 构建。
4. 需要维护旧版本时再切 `release/x.y`。

测试环境：cu 现在 `/data` 只剩约 8 GB，OceanBase 单机镜像要的内存与磁盘都不少，接之前先确认容量。
